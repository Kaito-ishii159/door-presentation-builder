# 固定レイアウト見積書の抽出・OCR検証

## 現時点の結論

実メーカーの見積書・正解データは未提供のため、実帳票の精度は未測定です。初期レイアウトは架空サンプル用で、メーカー帳票への適合を保証しません。実資料はコミットせず、ローカルの `private-fixtures/`（Git管理対象外）などで管理してください。

2026-11-03、Chromeで架空の4ページ・3建具について、PDF.js 4.10.38 / Tesseract.js 5.1.1（jpn+eng）を使用して検証しました。画像PDFは200dpiの架空画像をPDF化し、240dpi目標で再画像化、列別OCR、グレー化、信頼度下限60で処理しています。二値化はオフです。

- WD-2の設置場所 `洋室①` はOCR原文が `洋室 〇`、信頼度約52.7となり、出力は「要確認」でした。
- WD-3の型番は、3ページ目の `DEMO-F003` と4ページ目の `DEMO-PART030` が競合する意図的なテストです。先頭の商品へ勝手に決定せず「要確認」としました。文字そのものの誤読とは区別します。
- 上記2項目を手修正すると手修正後の比較は全項目3/3になり、抽出時点の比較は変化しないことを確認しました。
- 座標JSONだけの架空サンプルは構造テストです。PDF画像化もOCRも実行していないため、OCR精度とは表示・集計を区別します。

## 実帳票を投入する手順

1. 「見積書の読取・精度検証」で、列の順序、6点の境界、表の上下を設定します。値はページ全体に対する割合です。見積書PDFを選択すると、PDFテキストと文字位置で抽出し、原本プレビューを表示します。
2. プレビューで列境界を合わせます。必要なら行の高さ（0は文字座標で集約）、行の許容差、DPI、信頼度下限、二値化を調整し、テキストを再読取します。設定はレイアウトJSONで保存・復元できます。
3. スキャンPDFまたはテキスト層も検証したい場合、「画像PDFをOCRで読み取る」を手動実行します。OCRは表の各列を切り出して逐次実行し、各語の座標・信頼度を保持します。
4. 各候補と「全明細・候補」を確認します。空欄、形式不明、低信頼度、競合値は「要確認」です。部屋名の認識は図面上の開口部検出ではありません。
5. 原本を人が確認した正解JSONを出現順で作成し、読み込みます。「正解JSONひな形」の架空値は必ず置換し、実帳票の正解を確認した場合だけ `synthetic` を `false` にしてください。
6. 抽出時点と手修正後の項目別完全一致率、不一致一覧を確認します。「読取結果JSON」と「項目別精度・不一致一覧」をローカルに保存できます。

正解JSONの形式（5項目すべて、空欄・要確認は不可）:

```json
{
  "name": "原本確認済みの見積書",
  "synthetic": false,
  "items": [
    {"id":"WD-1","room":"玄関","sku":"DEMO-H001","type":"片引戸","size":"W1600 × H2400"}
  ]
}
```

## 抽出の方式とデータ構造

- 全文の先頭340文字に依存する従来方式を廃止し、PDF.jsの文字座標とTesseractの語座標を同じ正規化ページ座標へ変換します。PDFテキストが複数の語を1要素にまとめている場合、要素内の語の位置は幅から推定し、トークンに `positionEstimated` を残します。
- 各列の範囲に文字を振り分け、Y座標の許容差または設定した行高で明細行を作ります。列順も変更できます。現在は5列（建具番号・場所・型番・種類・寸法）のモデルです。
- WDごとに全明細を保持します。同じWDの再出現、番号の空欄行、連続した次ページ先頭の明細を集約します。ページ継続はオフにできます。単独の番号不明行・不正な番号は別の「要確認」レコードとして残します。
- 集約後、異なる型番や複数の幅・高さが見つかった場合は一つに決めません。扉・枠・金物などの明細を `details` にすべて保持します。実メーカーの部材種別ルールが未確定なため、代表型番の自動選択はしません。
- `review` は項目ごとの原文、ページ、Y位置、候補、OCR信頼度、要確認理由を保持します。信頼度はOCRエンジンの数値で、実際の正解率ではありません。
- `skuLookup` は `{raw, key, matchMode:"exact", status:"master-not-loaded"}`。将来の照合は承認したキーと商品マスタのSKU文字列の完全一致で行う想定です。0/O・1/I等を推測して置換せず、商品マスタ照合そのものは未実装です。
- 読取JSONは `source`、使用した `layout`、不変の `extractedItems`、`correctedItems`、警告・未割当行・精度結果を含みます。PDF原本は含みませんが、抽出文字に機密情報が含まれるため公開しないでください。
- 既存の「編集データJSON」はプレゼンボード用の編集値・図面・配置の保存用です。これを読み込む際、別の抽出結果と誤って比較しないよう読取・正解状態を解除します。監査用の読取JSONの再インポートは未実装です。

## 完全一致率の定義

同じ出現順のレコードを比較し、**各項目の完全一致件数 ÷ max(正解件数, 検出件数)** です。比較時の正規化・曖昧一致は行いません。「要確認」、空欄、余分な検出、検出漏れは不一致です。誤認識したWDで照合して番号精度を見かけ上100%にする方式は使いません。

正解は原本のWD初出順にそろえてください。途中に検出漏れ・余分なレコードがあると、それ以降の対応がずれる保守的な指標です。不一致一覧と原本でグループの対応を確認してください。項目単位の文字一致と、明細グループの正しさは別々に検収する必要があります。

## 制限と改善余地

- 実帳票の列境界、部材行、繰返し見出し、集計行を調整してから、異なる案件・画質・ページ数で検証する必要があります。傾き補正・台形補正・罫線除去・帳票の自動識別は未実装です。
- 一つのレイアウトを全ページに使います。ページごとに列や表範囲が変わる帳票、別々のW/H列、表の外にある設置場所には追加対応が必要です。
- 改ページ直後の番号なし行が本当に前のWDの続きかは、固定帳票の前提に依存します。原本のページと全明細で確認してください。
- 列別の一括OCRにより罫線や隣列の影響を減らしますが、丸数字や小さな英数字、型番の0/Oなどは依然として誤読し得ます。実商品マスタによる完全一致確認と人の最終確認が必要です。
- 初期ページ上限0は全ページ（最大200）。明示した上限で一部だけ読んだ場合、処理済み/総ページ数と部分検証の警告を表示します。画像は最大辺4000pxに制限し、DPI低下時は警告し実DPIを記録します。
- 大きな帳票は逐次処理でも時間・メモリが必要です。OCRの中止に対応し、失敗・中止では前回の結果を保持します。
- PDF処理、OCR、比較はブラウザ内です。PDF・画像・正解JSONをサーバーやAI APIに送りません。ライブラリ・言語データ・CMapはCDN取得のため、初回利用にはネット接続が必要です。完全オフライン運用にはセルフホストが別途必要です。
- 公開サイトは技術検証用です。実運用の合否は実帳票の項目別完全一致率、要確認率、未検出、誤った商品への一致、手修正時間、端末・ブラウザ互換性を測定して決めてください。

## 再現用コマンド

```bash
node --check assets/app.js
node --test tests/*.test.mjs
python3 scripts/make-ocr-fixtures.py --output /tmp/doorboard-ocr-qa --font /path/to/JapaneseFont.ttf
```

生成スクリプトはReportLabとPillowが必要です。macOSではArial Unicode.ttfを初期値にしています。生成物は架空資料ですが、実見積書と混在しないよう一時ディレクトリへ出力し、コミットしないでください。スキャンPDF、文字PDF、正解JSONを画面で投入して検証できます。

参照した一次資料: [Tesseract.js 5.1.1 API](https://github.com/naptha/tesseract.js/blob/v5.1.1/docs/api.md)、[PDF.js 4.10.38の画像化サンプル](https://github.com/mozilla/pdf.js/blob/v4.10.38/examples/learning/helloworld.html)。
